# OMS/EMS 与本项目交易链路说明

本文解释 OMS、EMS、撮合和报送的职责，盘点当前 UX Securities 项目中的相关实现，并给出继续建设的分阶段路径。

> 当前项目是港股个人交易终端 MVP，执行模式为模拟交易。文中真实券商/交易所接入属于未来扩展，不是现有能力，也不应在未获得供应商合同、权限、接口文档和用户授权前启用。

## 1. 名词解释

### OMS：订单管理系统

OMS（Order Management System）负责订单从用户提交到结束的生命周期。典型职责包括：

- 接收并记录订单请求，分配内部订单 ID，支持幂等键以防网络重试造成重复下单。
- 校验用户、证券、买卖方向、价格、数量、交易时段、余额/持仓和风险限制。
- 维护订单状态及状态变更时间，支持查询、撤单和订单历史。
- 接收成交结果并更新订单累计成交数量、均价、剩余数量和最终状态。
- 把成交交给账务/持仓模块，保存审计记录并向前端返回可解释结果。

订单状态不应只是随意改写的字符串，而应有明确状态迁移。例如：

```text
新订单 → 待处理 → 已报送 → 部分成交 → 全部成交
                  ↘ 已撤销
                  ↘ 已拒绝
```

实际状态集合取决于交易渠道。券商可能返回“已接收”“待确认”“部分成交”“撤单处理中”等状态；项目内部状态需要通过明确映射统一表达。

### EMS：交易执行管理系统

EMS（Execution Management System）负责“订单如何执行”。真实交易场景下，它通常管理执行渠道/券商连接、订单路由、执行回报、重试和通道故障。更高级的 EMS 还可能拆分大订单、选择执行策略和比较成交质量。

模拟交易 MVP 不需要连接真实 EMS。可以把当前内部模拟撮合器视作一个非常简化的模拟执行器，但它不具备券商路由、交易所协议、真实回报处理或执行策略。

### 撮合与执行

撮合是把买单和卖单按规则配对，确定“能不能成交、成交多少、成交价格是多少”。真实市场中，交易所通常按价格优先、同价时间优先等规则撮合，并受对手盘数量影响。模拟系统如果只有一个最新成交价，就不知道现在买方愿意出什么价、卖方愿意收什么价，也不知道对应价格有多少股票，因此不能准确还原真实成交。

#### 用买卖盘理解限价单

假设行情快照显示：

| 买卖盘 | 价格 | 可见数量 |
| --- | ---: | ---: |
| 最优买价（Bid） | 379.90 港元 | 1,000 股 |
| 最优卖价（Ask） | 380.10 港元 | 600 股 |
| 最新成交价（Last） | 380.00 港元 | - |

买单要和卖盘比较，卖单要和买盘比较：

- **买入限价 380.00 港元，数量 500 股**：卖方最低要 380.10 港元，高于买方愿付的最高价，因此不能立即成交，可留作待处理订单。
- **买入限价 381.00 港元，数量 500 股**：卖方报价 380.10 港元没有超过买方上限，按这个示例规则可成交 500 股，成交价可按对买方有利的卖方报价 380.10 港元，而不是直接按 381.00 港元扣款。
- **买入限价 381.00 港元，数量 800 股**：如果模拟器只把快照中的 600 股卖盘数量视为可成交量，则先成交 600 股，剩下 200 股继续挂单或按订单有效期取消。这称为部分成交。
- **卖出限价 379.90 港元，数量 500 股**：买方愿意出 379.90 港元，达到卖方最低接受价，因此可成交；示例成交价为 379.90 港元。
- **卖出限价 380.10 港元，数量 500 股**：最高买价只有 379.90 港元，低于卖方最低接受价，因此不能立即成交。

这说明最新成交价 380.00 港元并不能单独回答订单是否可成交：买入 380.00 港元可能暂时买不到，尽管最新一笔交易正好是 380.00 港元。Bid/Ask 和可见数量比 Last 更适合做这种模拟判定，但行情源必须确实提供这些字段，并且数据足够新鲜。

#### 当前系统实际如何处理

当前代码还没有按上面的买卖盘示例撮合。它会检查行情时间和交易时段，再由仓储层读取数据库中的证券 `last_price`：买入限价不低于该价格、或卖出限价不高于该价格，就按该参考价全额成交；否则订单保持 `pending`。因此当前行为是**单一价格阈值模拟**，没有使用 Bid/Ask 数量、价格队列、部分成交或持续重新撮合，也不能把它当成真实交易所撮合。

#### 怎样逐步改善模拟撮合

1. **先统一价格快照**：服务层完成新鲜度校验后，把同一份行情快照传给执行器用于判价和记录成交；不要判价用一个报价、结算时又读另一个数据库缓存价格。
2. **有可靠 Bid/Ask 时用对手盘价格**：买单比较 Ask 与限价，卖单比较 Bid 与限价；成交价按公开且固定的模拟规则计算，并记录所用快照时间、来源和状态。
3. **处理可见数量和部分成交**：行情源提供盘口数量时，模拟成交量不得超过可用数量；剩余数量可继续挂单或按有效期取消。订单状态需支持 `partially_filled`，每笔成交单独记入 fills/executions。
4. **定义行情不足时的降级行为**：若只有 Last、Bid/Ask 缺失、数据过期或行情状态不可用，应明确拒绝立即模拟成交或使用标记清楚的保守规则；不能默默假设有足够流动性。
5. **再考虑持续撮合**：新快照到达时重新检查有效的待处理订单，并处理重复行情、并发撤单与成交竞争，保证同一数量不会重复成交。

公开或延迟行情即使带有 Bid/Ask，也不等于实时、完整、可用于真实执行的盘口。模拟成交只用于产品演示和测试，不应产生真实订单，也不应宣传为真实市场成交结果。

### “报送”可能指两件不同的事

在交易语境里，“报送订单”通常是将订单通过执行通道发给券商或交易场所；这属于 EMS/券商接入能力。它不同于“报表/监管报送”，后者是按法规或市场规则生成并提交交易、客户或风险资料的合规流程。

当前项目两者都没有：订单只写入本地 MySQL 的模拟交易数据，不发送给券商/交易所；也没有监管申报、对账或正式交易报表模块。前端的订单历史是产品查询页面，不等于监管报送。

## 2. 当前系统已经具备什么

当前实现是模拟交易闭环中的一部分，可视作“基础 OMS + 单次价格判断的模拟执行”，不是完整 OMS/EMS 产品。

| 能力 | 当前情况 |
| --- | --- |
| 下单入口 | 已有认证的 `POST /api/v1/orders`，只接受模拟限价单。 |
| 幂等 | API 使用 `Idempotency-Key`，数据库以用户和 client order ID 建唯一约束，减少请求重试导致的重复订单。 |
| 基础检查 | 检查字段、行情新鲜度、港股连续交易时段、整手数量，以及买入余额/卖出持仓。 |
| 模拟撮合 | 买入限价不低于数据库证券参考价，或卖出限价不高于参考价时，立即全额成交；否则成为 `pending`。 |
| 账户与持仓 | 成交时在同一数据库事务里更新虚拟现金和持仓；按用户隔离。 |
| 撤单 | 可以撤销仍处于 `pending` 的模拟订单。 |
| 订单查询 | 支持按用户查看订单历史，并按证券、方向、状态和时间范围筛选。 |
| 真实执行通道 | 不存在；OpenAPI 明确说明没有真实 execution venue。 |
| 监管/正式报送 | 不存在。 |

主要实现位置：

- 订单服务和交易时段/行情检查：`apps/backend/internal/service/trading/service.go`
- 模拟成交、虚拟现金和持仓事务：`apps/backend/internal/repository/mysqlrepo/trading.go`
- 订单、持仓表和唯一幂等约束：`db/migrations/003_paper_trading_orders_positions.sql`
- 订单 API 合同：`docs/api/openapi.yaml`
- 模拟下单界面：`apps/frontend/src/pages/TradingPanel.tsx`

## 3. 当前实现的边界与不足

当前版本适合演示和产品闭环验证，但不应被描述为生产级 OMS/EMS：

1. **撮合过于简化**：只看一个证券参考价，不使用买卖盘口、可成交量、市场深度、价格-时间优先级或滑点模型。
2. **没有持续撮合**：未成交订单创建后保存为 `pending`，当前没有后台撮合工作器在新行情到达时再次检查这些订单。
3. **不支持部分成交**：数据结构有 `filled_quantity`，但当前规则是全额成交或完全未成交；没有独立 executions/fills 表来记录多笔成交。
4. **参考价口径需统一**：服务层获取并校验行情后调用结算；仓储结算又读取 `stocks.last_price` 作撮合和成交价。实施前应明确以同一份带时间戳行情作为判价与成交依据，避免报价与数据库缓存不一致。
5. **拒绝状态未形成完整业务记录**：虽然 schema 定义了 `rejected` 和 `reject_reason`，但余额不足、持仓不足、市场关闭等情形当前以 API 错误返回为主，不一定落成一笔可查询的 rejected 订单。
6. **风控范围有限**：已有余额、持仓、手数、市场时段和行情新鲜度检查，但没有融资额度、保证金、折算率、追保/强平、集中度或多币种风控。
7. **缺少外部执行生命周期**：没有券商订单 ID、通道状态、执行回报、撤单确认、拒单原因映射、超时对账、重复回报去重和通道健康监控。
8. **缺少正式审计/报送能力**：订单和成交可供应用查询，但没有不可变的事件流水、对账文件或监管申报。

## 4. 推荐的模拟 OMS/撮合建设顺序

如果目标是先把模拟交易做好，可以按以下顺序补齐，不需要先引入真实 EMS：

### 阶段 A：把订单生命周期定义清楚

- 定义订单状态、允许的状态迁移、每个失败分支及前端文案。
- 将“订单已接收”和“订单已成交”区分开；对失败请求确定是返回 API 错误，还是创建一笔带拒绝原因的 rejected 订单，并保持合同一致。
- 保存订单事件时间和触发原因，禁止通过任意更新跳过非法状态迁移。
- 明确限价单的有效期，例如当日有效或持续有效，以及市场休市、停牌、行情过期时如何处理。

### 阶段 B：分离订单、执行和成交记录

建议的逻辑职责：

```text
HTTP Handler
  → Order Service（身份、输入、幂等与订单状态）
  → Risk Checks（现金、持仓、交易时段、行情状态）
  → Execution Port（模拟执行器；未来可有券商适配器）
  → Fill Service（成交入账、持仓/现金更新）
  → MySQL transaction + order events
```

至少要区分订单主记录和成交明细：

- `orders`：用户订单意图、限价、原始数量、当前状态、剩余数量和幂等键。
- `executions` 或 `fills`：每一笔成交的数量、价格、时间、费用、来源及外部执行 ID（模拟时可为空）。
- `order_events`：订单状态变化、原因和请求/关联 ID，供审计、排障和重放检查。

数据库迁移前应先确定金额精度、唯一键、事务边界、并发锁和 down migration。不能仅靠覆盖 `orders.status` 保留完整成交历史。

### 阶段 C：建立可重复的模拟执行模型

- 将模拟执行器定义为接口，输入订单和带来源/时间戳的行情，输出执行结果；不要让 handler 自己改余额或持仓。
- 先实现清晰且可测试的规则：价格条件、订单有效期、行情过期、整手/最小数量、模拟费用和现金冻结。
- 若要支持挂单后成交，行情更新或定时扫描应触发待处理订单重新评估；需防止同一订单重复成交，并在事务中锁定订单及账户。
- 若要支持部分成交，执行器必须返回多笔 fill，OMS 维护累计成交量和剩余量，状态应能表示 `partially_filled`；同时更新前端和 API 合同。
- 将用于判价的行情快照固定在成交事件中，保存 `source`、`data_status` 和 `as_of`，让用户能理解模拟成交依据。

### 阶段 D：补齐运营能力

- 订单列表支持状态和失败原因，提供订单详情/事件时间线。
- 建立幂等、并发下单、重复撤单、撤单与成交竞争、余额不足回滚等集成测试。
- 建立可关联但脱敏的 request/order/event 日志和指标；不得记录凭据或原始敏感供应商载荷。
- 若要对账，应先定义内部订单、成交、账务流水之间的可核对合同；模拟对账与监管报送是不同工作。

## 5. 将来接入真实 EMS 的前置条件

真实执行应通过独立的 `ExecutionAdapter`/execution port 接入获准券商或交易参与者 API，而不是把真实 HTTP/WebSocket 调用塞入现有模拟撮合代码。至少需要：

- 已签订的供应商/券商合同、已审核的接口文档、环境凭据管理和用户交易授权。
- 明确账户、市场、币种、订单类型、交易时段、手数、费用、融资与风险规则。
- 对内部订单状态与券商状态做映射；处理确认、部分成交、拒单、撤单中/撤单确认、超时和未知结果。
- 对每个请求设置稳定的外部 client order ID；处理网络超时后“请求可能已成功”的不确定结果，先查询/对账再决定是否重试，避免重复真实下单。
- 对券商回报进行验签/认证、去重和顺序处理；成交入账与状态更新具备可恢复性。
- 上线前完成权限分级、人工/用户确认、限额、熔断、审计、告警、对账、灾难恢复和合规审批。

建议架构边界：

```text
OMS（内部统一订单状态）
  ├─ PaperExecutionAdapter（当前模拟路径）
  └─ BrokerExecutionAdapter（未来；需独立授权与审批）
```

市场行情授权和真实下单权限是两项独立能力。接入行情源不代表可以交易；模拟执行也不能因为使用公开行情而转成真实下单。

## 6. 结论

当前系统**有订单管理和模拟成交的基础实现**：可以创建模拟限价单、做若干预检查、按简化参考价全额成交或挂起、更新虚拟账户，并查询/撤销待处理订单。它还不是完整 OMS，更没有真实 EMS 或订单报送功能。下一步应先把模拟订单状态、成交明细、持续撮合和可审计账务做好；只有获得真实交易所需的授权、合同、接口和风控批准后，才设计并实现独立券商执行适配器。
